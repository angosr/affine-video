# Veda Bittensor 子网实现设计

本文说明工程边界和各机制如何衔接。评分与数据细节见
[数据流水线设计](GPU_EVALUATION_DATA_PIPELINE_DESIGN.md)，存储与恢复见
[运维说明](PRIVATE_STORAGE_OPERATIONS.md)，参赛操作见 [README](../README.md)。
活动模型参数、预算和阈值以固定公开路径的 `track.json` 为准。

## 1. 工程边界

Veda 是 SN120 mechanism 1 的选块器训练竞赛。Miner 提交权重，
评测器按链上顺序挑战当前冠军；独立 Validator 读取公开推荐并设权。

现网e49／r9仍按公开冻结的双阶段规范运行。已提交的候选
`promotion.format=veda-exact-tenure-v1`为「仅exact＋冠军任职门槛线性衰减」，
仅源码及定向CPU通过，尚未构建、冻结或部署；下文明确区分候选与原双阶段历史，
不能因仓库候选变化声称线上规则已变。

仅有三个业务包：

- `src/miner`：本地模型准备与一次性链上提交。
- `src/scoring`：模型校验、exact 配对评分和完整视频质量计算。
- `src/validator`：链扫描、FIFO、数据生产、持久化、公开发布和独立设权。

`src/cli.py` 和 `src/monitor.py` 是入口与公开展示。`validator/production`
属于评测系统内部能力，不是第四个业务包。
Miner 没有常驻服务；评测器不持有 Validator 钱包。
producer 与 evaluator 分别运行，披露是 evaluator 内部任务，不增加独立调度服务。

## 2. 提交、归属与机会

链上 payload 保持：

```text
VDA1 | repo_id 字节长度 | repo_id ASCII | revision 的 20 字节
```

Miner 提交 HF 模型仓库名与完整40位 revision。扫描器只读取最终确认区块，
按区块、extrinsic、event 位置排序，支持普通 commitment 和 timelock reveal。
无法匹配、歧义或无法解码的 reveal 记录告警后跳过，不停止整条扫描链路。

已激活老赛事的 hotkey 不得参加 VEDA；VEDA 参与者后来激活老赛事也会失去奖励资格。
普通注册不等于旧赛激活。重复 VEDA 提交单独识别，不把它误分类为旧赛事参与。

每个 hotkey 只有一次正式评测机会，跨维护保留。格式错误、模型无效或挑战未胜出会消耗机会。
仅原提交时没有该冻结策略所需合格题库的 `SYSTEM_NOT_ADMITTED` 保留机会、允许以后重新提交；
现网双阶段需两份独立数据，候选仅exact需一份原S合格READY。
基础设施重试恢复同一挑战，不授权更换模型或重提。

UID0 使用规范绑定的 VEDA 基准作为初始冠军，不实际提交；UID0 提交会被拒绝。

## 3. 模型准入

固定 revision 根目录提供 `selector.safetensors`，schema 由赛道和
`scoring/model.py` 校验。只含指定的 query/key 投影及所属 hotkey metadata，
不包含可执行代码、额外 tensor、适配器或基础模型补丁。

同时计算两种指纹：

- `file_sha256` 覆盖完整文件及 metadata，用于下载和归档完整性。
- `model_digest` 覆盖规范化 tensor 内容，识别换 hotkey、重打包后的同一模型。

FIFO 轮到提交时，固定文件必须可匿名下载。完整校验及离机模型归档成功后准入；
最早通过准入的 hotkey 取得模型指纹归属，后续重复模型拒绝。
归档后恢复使用原模型，不依赖 HF 仓库持续存在。

## 4. 数据资格与分配

producer 不依赖新提交，持续按数量和全盘字节水位提前补池。
每份计划绑定真实 finalized 区块及独立随机秘密，条件创建后不可换种子。
完成全部字节校验才封存 READY，记录实际 UTC 完成时间和保守链高度边界。

设完成为 C、原最终确认提交为 S、披露时刻为 R=C+24小时：

- READY 完成链边界严格早于 S，且原 S 的链上 Timestamp 满足 C<S<R。
- S 时数据仍秘密。迟扫描、排队或重启不改变 S 和资格集合。
- 按固定规则取最近合格库存；同一 READY 可供多个模型使用，不逐模型生产或消耗整批。
- 原双阶段策略的exact与full-video使用相反来源槽且source family无交集；
  候选仅分配exact，不领取第二批或伪造full阶段。
- 私有单一 CAS 分配固定挑战、阶段、模型双指纹、S和READY；重试沿原绑定。
- 模型固定 revision 后允许跨 R 完成，但到期后的新提交不能领取该数据。

原 S 无合格集合与数据暂时缺失不同；后者必须恢复原字节并退避，不能改用未来数据。
源池、秘密承诺及披露后的重算规则由数据流水线设计定义。

## 5. 对战与评分

严格 FIFO：后续挑战不越过未完成的前序挑战。
没有全赛截止或总挑战名额。

现网冻结的双阶段规则及其原历史：

1. `SCORING`：在相同 Q/K/V、dense reference、路线和预算下评测双方选块器。
   用冻结成本轴聚合多个预算的质量，以视频及相关 route/step 聚类计算配对下界。
2. `CONFIRMING`：exact 过线后，在独立来源数据上执行双方完整视频推理；
   比较 latent、轨迹和时空特征质量，按视频聚类计算配对下界。
3. 两阶段均超过规范门槛才晋升；平局或任一门槛未过都保留冠军。

候选规则（未上线）：只执行一次上述配对exact评测，不创建full-video worker，
不转入`CONFIRMING`。置信度仍为0.9975，LCB算法不改、不换中位数；
仅当`LCB > theta(S)`才为`CHALLENGER_WON`，等于门槛仍保留冠军。

设`T(B)`为原finalized块B的链上Timestamp（秒），`B_c`为当前冠军的真实建立块：

```text
age(S) = max(T(S) - T(B_c), 0)
theta(S) = 0.003 - 0.001 * min(age(S) / 604800, 1)
```

门槛从0.003连续线性下降，半周为0.0025，7天时为0.002，之后保持0.002。
原S锁定当场时钟，不使用执行墙钟，排队或评分延迟不改变门槛。
基线建立块从最早认证历史的`incumbent_before`恢复，真正换冠军以原胜场
`decided_block`重置；败场同题score刷新、重启或维护不重置任期。
缺少原建立事实或原块时间按基础设施异常暂缓，不猜时间、不用新track start替代。
阶段及新match携带原冠军ID、建立块及链时间、原S及链时间和实际门槛，
与原allocation时间一致，供publication、Reader、恢复和状态展示统一复算；
复用原阶段记录，不另建任期账本。

成本轴取赛道冻结的 `calibrated_cost`，不是当场计时，也不意味着换硬件后已重新校准。
不同数据上的绝对分数不直接比较，胜负使用同题配对结果。
成功完成计算与赢得挑战是不同状态，公开 `outcome` 才表示胜负。

格式和确定性模型错误正常终结；链、HF、存储或计算基础设施异常不判矿工输。
有限快速重试耗尽后持久冷却、自动探测原阶段，保留 FIFO、绑定和机会。
评分结束后重读 finalized head，先归档阶段再提交本地状态。

## 6. 持久化与隔离

私有对象存储是生成计划、READY、分配、准入、模型、阶段和重试的权威来源；
必须支持真实 CAS。本地 SQLite 和缓存是可重建投影。

隐藏视频、latent、Q/K/V及选定输入大文件保存在 GPU 本地。
恢复优先使用原阶段和原 hash；已公开内容可按原分片完整校验下载。
永久无法恢复的 READY 字节仍是恢复边界，不自动换题、不改写原成绩。

producer 可读完整隐藏源池；evaluator 只挂载评分必需资产和当前选定数据，
不能通过对象权限或本地挂载读到整个源池。模型与必要运行资产离 GPU 保全。
权限由冻结源码生成、用实际角色验证。

## 7. 公开结果与延迟披露

所有公开对象沿用唯一 `tracks/main/` 前缀：

| 路径 | 职责 |
| --- | --- |
| `track.json` | 活动规范及运行资产摘要 |
| `weights.json` | Validator 消费的唯一权重推荐 |
| `summary.json`、`status.json` | 有界排行、队列、阶段及比分 |
| `matches/<track_id>/<sequence>.json` | 不可变对战事实 |
| `runtime/<manifest_sha256>/manifest.json` | 规范绑定的运行资产索引 |
| `batch_groups/`、`batches/`、`batch_assets/`、`batch_inputs/` | 到期披露及重放数据 |
| `models/` | 按原对战引用的模型归档 |
| `system_matches/` | 发布证据，不参与矿工排名 |

安全聚合分数和承诺可及时展示。正式 match/weights 在公共模型归档完整后发布，
不等待原始评测大文件；不能把模型归档耗时称为零延迟。
每份 READY 按自己的 R 披露，未使用的数据也披露，不等挑战终态。
披露前详情不包含 prompt、种子或可重建输入，完整独立复算在披露后进行。

公开存储使用唯一 writer、共享锁、历史单调校验和写后核验，不假定分布式原子发布。
依赖对象先于引用它的不可变事实，weights 先于展示文件；
权重绑定连续对战前缀及末场摘要，较新高度不能覆盖冲突历史或回退冠军。

## 8. 设权与维护

Validator 只读固定公开 URL，校验赛道、机制、时效、对战前缀和最终确认 hotkey 映射，
用自己的钱包设权，不需要存储密钥或评测数据。
有效冠军获得本机制全部权重；其失去资格时按既有链上规则使用已注册基准回退。
无有效推荐时不发送新的权重交易。

维护保留已确认冠军、全部原赛果、已用机会及模型去重。
历史按原 key、SHA及身份引用，不复制到新身份或按新阈值重判；
新 track 的比赛序号只在自己的命名空间重新计数。
空库恢复先核原链上提交和全部历史，再允许新 FIFO。

兼容软件维护的运行manifest／source／lock／实际OCI／accepted与比赛承诺分离，
保原比赛manifest、DB、cursor及READY；运行身份由公开status.runtime_release披露。
本候选改变晋升规则，不能借兼容runtime维护热塞旧r9：未来上线须正常绑定新规则身份，
沿原认证历史／fence承接原key和SHA，不手列场数、复制机会或重判旧成绩。
旧双阶段赢家及旧模型引用仍按原事实读取恢复；候选私有exact真赢家才公开模型，
私有败场只公开赛果／成绩／哈希，权重保留原私有归档。

发布门禁由 `validator/release.py` 验证 E2数值一致性、E3两阶段GPU执行、
E16确定性与异常处理，并绑定实际源码、环境及资产。
这里的E3是原科学报告的测量范围，不代表候选仍运行full阶段或须伪造新的两阶段成绩。
历史证据保留原source／硬件及执行身份，新候选兼容及CPU边界证明独立说明，
不把报告复用冒称重测；研究诊断不作为额外上线清单。
切换前交付完整摘要及外部 pin 更新信息，先停旧 writer 再启新 writer，
公开 URL 和链上提交协议不变。部署步骤见运维说明。
